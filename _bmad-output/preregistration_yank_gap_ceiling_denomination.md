## 0. The defect

`detect_fvg` (`src/research/strategy_core.py:387-390`) gates one quantity — the FVG gap
size — with two thresholds that are denominated differently:

```python
if gap_pts * POINT_VALUE_USD > config.max_gap_dollars:      # 60.0  ABSOLUTE currency
    return None
if atr > 0 and gap_pts < config.min_gap_atr_ratio * atr:    # 0.25  SCALE-FREE
    return None
```

The set of gap sizes satisfying both is

```
[ min_gap_atr_ratio × H1_ATR ,  max_gap_dollars / POINT_VALUE_USD ]
```

which is **empty** whenever

```
H1_ATR  >  max_gap_dollars / (POINT_VALUE_USD × min_gap_atr_ratio)   =  120 index points
```

The floor rescales with the market. The ceiling does not. As MNQ's hourly range grew, the
fixed ceiling walked into the scale-free floor and closed the interval between them.

### 0.1 Measured, on the bot's own recorded bars

`logs/yank_shadow_parity.csv`, via `tools/fvg_feasibility.py`:

| Period | median H1 ATR | % H1 bars with **empty** window | median feasible width |
|---|---|---|---|
| 2026-06 | 133.0 | **62.7%** | **0.0 pts** |
| 2026-07 | 123.1 | **55.0%** | **0.0 pts** |
| 2026-08 (to 08-07) | 105.0 | 12.3% | 3.8 pts |

For the **median hour** of June and July 2026 there was no gap size of any magnitude that
could pass. Live consequence: YANK's last fill was 2026-07-22; the funnel shows **705 bars
since 2026-08-02 with H1 sweep active AND M15 CHoCH confirmed, and zero FVG detected.**

### 0.2 This is not a parity defect

The live bot is faithful to its seal. `detect_fvg` is shared code — the sealed backtest
applies the identical two lines and would go equally silent over the same bars. Nothing
diverged. **A constant aged out.** That distinction governs everything below: there is no
"repair" available that restores a previously-correct behaviour, because the behaviour was
never different.

## 1. The honest framing — this is a strategy change, not a bug fix

The tempting story is "restore the ceiling's original intent, expressed scale-free." That
story is **false**, and the disclosure that kills it is this:

Over the derivation era (2025-01-01 → 2026-02-28, strictly pre-holdout), at the currently
live floor of 0.25, the window was **already empty for 19.7% of H1 bars** — reaching 47.7%
(2025-03), 45.3% (2025-06), 44.4% (2025-12). At the pre-S25 floor of 0.15 it was empty
12.9% of the time.

**So every backtest, walk-forward, and OOS result YANK has ever produced was generated by a
strategy that was intermittently blind, and the blindness is baked into those results.**
Removing it does not recover a lost edge. It creates a system whose accepted-gap population
differs from anything that has been validated.

This prereg therefore does **not** claim to fix a bug. It pre-commits to a procedure for
deciding between two responses, and to the evidence cost of each:

| | Response | Cost |
|---|---|---|
| **A** | Re-denominate the ceiling in ATR units | YANK becomes a system the sealed OOS does not describe; re-validation required (§6) |
| **B** | Leave the gate alone | Accept that YANK fires only in low-ATR regimes and that its trade rate is a function of volatility, not of edge; document it and stop calling the silence a defect |

**Neither is pre-favoured.** §5 decides between them on evidence.

## 2. Hypothesis

**H₁ (denomination):** the `$60` ceiling and the `0.25 × ATR` floor are a *denomination
mismatch*, not two independent design choices. If so, re-expressing the ceiling in ATR units
at its historical-equivalent value will reproduce the old gate's accept/reject decisions on
the sub-period where the old ceiling was **not** binding, while eliminating the empty-window
state by construction.

**H₀:** the two thresholds encode genuinely independent intents (an absolute risk-per-trade
ceiling and a relative-significance floor). Re-denomination then changes which trades the
system takes, and must be evaluated as a new strategy, not as a correction.

H₁ is falsifiable and §5 is its test. **A pass on §5 is a claim about denomination only — it
is never evidence that the changed system is more profitable.**

---

## 3. Derivation of the candidate ceiling (no asserted value)

Per the standing rule (*derive, don't assert*): the new constant is **not** chosen for
performance and is **not** hand-set. It is derived from what the existing ceiling was
worth, in ATR units, over the era in which it was introduced and validated.

**Provenance of the existing value.** `max_gap_dollars = 60.0` first appears in commit
`96320e8` (2026-04-17, *"Complete TIER 1 FVG Foundation System with walk-forward
validation"*). Its validating era therefore predates the sealed holdout (opens 2026-03-01).

**Derivation window (pre-committed, entirely pre-holdout):** 2025-01-01 → 2026-02-28, from
`data/processed/dollar_bars/1_minute/mnq_1min_2025.csv` and `mnq_1min_2026_ytd.csv`.
**The sealed holdout is NOT read by this derivation and must not be.**

**Statistic:** the hourly series `cap_pts / H1_ATR`, where `cap_pts = max_gap_dollars /
POINT_VALUE_USD = 30.0` and `H1_ATR` is the live `calc_atr` (20-bar mean TR) on H1 bars.
Point estimate = **median**, pre-committed before computation, chosen because it is the
location statistic least sensitive to the fat right tail of ATR.

**Result (computed 2026-08-07, before seal — see §8 for a-priori/derived disclosure):**

```
H1 ATR over the era:  median 70.5   p25 49.9   p75 102.1   (index points)

cap_pts / H1_ATR :  p10 0.129 | p25 0.294 | p50 0.426 | p75 0.601 | p90 0.768 | mean 0.454

  →  derived  max_gap_atr_ratio = 0.426
```

**Structural property of the derived value:** `0.426 > min_gap_atr_ratio = 0.25`, so under
Response A the feasible window is non-empty **for every ATR, by construction**. The failure
mode of §0 becomes unreachable rather than unlikely. This property — not the specific
number — is the point of the change.

**No sweep is authorized.** The value is fixed by the procedure above. If §5 fails, the
answer is Response B, **not** a search for a ratio that passes.

## 4. Change spec (the only diff, one knob)

Conditional on §5 PASS and an explicit go from Alex.

1. `StrategyConfig` gains `max_gap_atr_ratio: float = 0.426`. `max_gap_dollars` is
   **retained** and defaults unchanged, so every existing sealed doc and stored config
   continues to parse and to mean what it meant.
2. `detect_fvg` replaces the currency ceiling with the ATR ceiling **only when
   `max_gap_atr_ratio > 0` and `atr > 0`**; otherwise the `max_gap_dollars` branch is used
   verbatim. Old configs are bit-identical in behaviour.
3. `strategy_config.yaml` gains `max_gap_atr_ratio: 0.426`.
4. Nothing else. Not `min_gap_atr_ratio`, not `atr_threshold`, not CHoCH, not SL/TP, not
   the ML threshold. One knob.

## 5. Acceptance gate (binary, falsifiable, pre-committed)

Run **before** any deployment, on the derivation window only (§3), by replaying `detect_fvg`
bar-by-bar under the old and new ceilings and recording every 3-bar FVG candidate.

Define the **non-binding sub-period** as H1 bars where *neither* ceiling was the operative
constraint — i.e. `0.25 × ATR ≤ 30` **and** `0.25 × ATR ≤ 0.426 × ATR` (the latter always
true), which reduces to `H1_ATR ≤ 120`. On that sub-period the two gates should agree if H₁
holds.

| | Criterion | Bar |
|---|---|---|
| **G1** | Accept/reject agreement on FVG candidates over the non-binding sub-period | **≥ 97%** |
| **G2** | Empty-window H1 bars under the new ceiling, whole derivation window | **exactly 0** (structural; any non-zero is an implementation error) |
| **G3** | Median accepted `gap_pts` shifts by | **≤ 10%** over the non-binding sub-period |
| **G4** | `tools/fvg_feasibility.py` reports `level=0` over the last 30 days of live bars under the new config | required |

**G1 and G3 are the H₁ test.** If either fails, H₁ is rejected: the thresholds encoded
independent intents, the change is a strategy change with no denominational justification,
and the pre-committed outcome is **Response B (§1)** — leave the gate alone and document the
volatility-dependence as a known property.

**A pass on G1–G4 authorizes the code change and nothing else.** It does not authorize
deployment (§7), and it is not evidence about profitability.

## 6. What a PASS costs — and it is not free

If §5 passes and the change ships, YANK's accepted-trade population changes in exactly the
regime where it previously accepted nothing (H1 ATR > 120). **The sealed OOS result that
justified the current config (`preregistration_yank_sl2tp8_ml050.md`, 2026 holdout, PF
≈1.60) was produced under the old ceiling and does not describe the changed system in that
regime.**

Pre-committed consequences, accepted in advance:

1. **YANK's live evaluation clock restarts at zero on deployment.** Trades before the change
   may not be pooled with trades after it. This mirrors the ruling in
   `preregistration_mim_nb_post_repair_evaluation.md` §1.
2. **The sealed 2026 holdout is spent and will NOT be re-run.** There is no second holdout.
   Re-validation of the changed system, if pursued, requires either fresh post-holdout data
   or a prospective live sample — and the prospective sample is the slow path this program
   already knows the price of (mean $168.50, sd $399.09 → N≈44 for 80% power at the
   observed live effect, ≈ 36 weeks at 0.97 trades/week).
3. **Gate-Minus-One applies.** One broker-confirmed round trip on the changed code before
   any subsequent analysis counts, per the standing rule from the Thursday-Short pivot.

The honest summary: this change **buys signal frequency and costs validation standing**.
Whether that trade is worth making is Alex's call and is explicitly not decided here.

### Implementation deviation from §4 (disclosed, not silent)

§4.1 specified `StrategyConfig` should gain `max_gap_atr_ratio: float = 0.426` (default
ON) and §4.3 specified `strategy_config.yaml` gains the same key. Implementation found
a hazard §4 did not anticipate: **`strategy_config.yaml` is shared** — `s26_soft_fvg` and
`s26-combine` resolve the identical default-YAML path (`STRATEGY_CONFIG_PATH` env var,
else repo-root `strategy_config.yaml`, else dataclass defaults) via the same
`detect_fvg`/`StrategyConfig` code YANK uses. A YAML-level `max_gap_atr_ratio` would have
silently re-denominated their gap ceiling too — never authorized by this seal (scope is
YANK-only throughout; §7 forbids touching MIM-NB, says nothing that would extend scope
to s26/s26-combine either).

Shipped instead, functionally equivalent for YANK, zero blast radius for the other bots:

1. `StrategyConfig.max_gap_atr_ratio` defaults to **0.0** (disabled), not 0.426 — matches
   the file's existing "0.0 = off" convention (`ml_threshold`) and every other bot's
   `StrategyConfig()` stays bit-identical without needing to know this field exists.
2. `detect_fvg` (`strategy_core.py`): unchanged logic otherwise — `if max_gap_atr_ratio>0
   and atr>0: ceiling = max_gap_atr_ratio*atr; else: ceiling = max_gap_dollars` (verbatim
   §4.2 semantics).
3. `strategy_config.yaml` **not touched**. Ratio is set via a YANK-only env var
   (`YANK_MAX_GAP_ATR_RATIO=0.426`), read once in `yank_streaming_working.py::
   _build_strategy_config`, applied via `dataclasses.replace()` after the shared YAML
   loads — layered on top, not baked into the shared file.

One knob, YANK-scoped, still true to §4's "nothing else" — the mechanism moved, the
diff's effect on YANK did not.
